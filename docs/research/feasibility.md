# Этап 0: техническая осуществимость ConnectX

## Уточнённая цель

ConnectX должен быть автономным Android-инструментом противодействия DPI, концептуально похожим на zapret/GoodbyeDPI: трафик не отправляется на сервер ConnectX, а локально изменяется его наблюдаемое DPI представление.

Термин «шифрование» здесь нельзя использовать как обещание дополнительной криптографии. HTTPS уже шифрует полезную нагрузку; локальное приложение без удалённой стороны может применять обфускацию, фрагментацию, десинхронизацию и другие способы затруднить классификацию или блокировку соединения.

## Почему на Android всё равно рассматривается `VpnService`

Без root обычное Android-приложение не может подключить WinDivert, NFQUEUE или произвольно изменять системные пакеты других приложений. `VpnService` предоставляет локальный TUN-интерфейс. Он может использоваться как точка перехвата, даже когда нет удалённого VPN-сервера.

Исходящие сокеты локального движка должны защищаться через `VpnService.protect()`, после чего они идут напрямую через базовую сеть и не возвращаются в TUN.

## Отличие от Windows-сборки Flowseal

Flowseal/zapret-discord-youtube — Windows-обвязка вокруг zapret и готовых стратегий. Её batch/PowerShell-логику и Windows packet interception нельзя перенести на Android напрямую.

Необходимо переносить не скрипты, а проверять применимость базовых идей:

- TCP segmentation и изменение границ отправки;
- fake/desync-пакеты;
- overlap и порядок сегментов;
- TTL/hop-limit техники;
- HTTP/TLS классификация по минимальным метаданным;
- UDP/QUIC стратегии;
- доменные и IP-фильтры.

## Матрица предварительной реализуемости

| Возможность | Без root через локальный TUN | С root | Статус |
|---|---:|---:|---|
| Прямой выход без сервера ConnectX | Да | Да | Архитектурно подтверждается Android API |
| Перехват трафика всех приложений | Да, через `VpnService` | Да | Требует системного согласия |
| Простое дробление данных при userspace TCP proxy | Вероятно | Да | Нужен прототип |
| Произвольная подмена TCP seq/ack исходных системных потоков | Ограниченно/нет | Вероятно | Зависит от полного userspace stack или packet path |
| Fake-пакеты с точным TTL | Сложно и зависит от движка | Вероятно | Нужны тесты на Android и сетях |
| WinDivert-перенос | Нет | Нет | Windows-only подход |
| NFQUEUE/nftables | Нет | Возможно | Требует root и поддержки ядра |
| HTTPS MITM | Не требуется | Не требуется | Запрещено архитектурой |
| Полная невидимость назначения для ISP | Нет | Нет | Без удалённого туннеля ISP видит IP и часть метаданных |
| QUIC/UDP обработка | Вероятно | Вероятно | Отдельный сложный этап |

## Главный технический риск

Локальный TUN сам по себе не является packet interceptor уровня WinDivert/NFQUEUE. Чтобы пропускать весь трафик, приложение должно реализовать или интегрировать userspace TCP/IP-путь: например, TCP/UDP proxy, tun2socks-подобную схему или полноценный netstack.

Это означает, что первая задача — не красивый интерфейс и не десятки стратегий, а доказательство стабильного прямого passthrough без удалённого сервера.

## Первый эксперимент

MVP сетевого эксперимента должен:

1. создать Android-проект и foreground `VpnService`;
2. создать локальный TUN;
3. читать IPv4-пакеты;
4. классифицировать TCP/UDP без журналирования payload;
5. открыть защищённые прямые сокеты к реальному назначению;
6. вернуть ответы в TUN;
7. доказать отсутствие циклов и удалённого промежуточного сервера;
8. добавить одну экспериментальную точку сегментации TLS ClientHello;
9. измерить доступность, ошибки, CPU и батарею;
10. не заявлять обход рабочим до испытаний.

## Решение на текущий момент

- Kotlin + Compose для Android-слоя.
- Native-движок будет выбран после сравнения Rust/C++ и существующих сетевых стеков.
- `VpnService` в режиме без root — только локальный механизм TUN.
- Root-режим проектируется отдельно и не входит в первый прототип.
- Никаких удалённых серверов ConnectX.
- Никакого MITM и установки сертификатов.
