# ADR-0001: userspace-сетевой движок ConnectX v0.2

Статус: **принято для прототипа v0.2.0-alpha.1**  
Дата: 2026-08-02

## Контекст

Android без root предоставляет приложению локальный IP-интерфейс через `VpnService.Builder.establish()`. Чтение файлового дескриптора возвращает исходящие IP-пакеты, а запись инжектирует входящие пакеты обратно в Android.

Сам `VpnService` не реализует TCP/IP stack. Чтобы направить TUN-трафик прямо к реальным адресатам без удалённого VPN-сервера, ConnectX нужен userspace stack, который:

- принимает IPv4/IPv6 пакеты из TUN;
- поддерживает TCP и UDP;
- создаёт реальные исходящие сокеты;
- позволяет защитить эти сокеты через `VpnService.protect()`;
- предоставляет точку для будущей DPI-обфускации;
- имеет лицензию, допустимую для закрытого приложения.

## Решение

Для прототипа выбран следующий конвейер:

```text
Android apps
    ↓
VpnService TUN fd
    ↓
tun2socks / gVisor netstack (сборка из исходников)
    ↓
локальный SOCKS5 endpoint ConnectX на 127.0.0.1
    ↓
DirectTcpRelay / будущий DirectUdpRelay
    ↓
VpnService.protect(outbound socket)
    ↓
реальный сервер назначения
```

SOCKS5 здесь является только внутренним интерфейсом между двумя локальными компонентами. Пользовательский трафик не отправляется на SOCKS/VPN-сервер разработчика.

## Выбранная основа

### xjasonlyu/tun2socks v2.6.0

- userspace stack: gVisor netstack;
- лицензия проекта: MIT;
- поддерживает FD-based TUN;
- поддерживает TCP и UDP;
- активно развивался до релиза v2.6.0;
- исходники должны собираться в CI, готовые сторонние бинарники в репозиторий не добавляются.

### gVisor netstack

- лицензия: Apache-2.0;
- полноценный userspace TCP/IP stack;
- используется как библиотечная основа tun2socks;
- увеличивает размер приложения и требует отдельного профилирования CPU, памяти и батареи.

## Почему не собственный TCP stack

Реализация TCP целиком с нуля требует корректной поддержки sequence numbers, retransmission, congestion control, window scaling, half-close, timeouts и большого числа пограничных случаев. Для первой рабочей версии это создаёт неприемлемый риск повреждения соединений и утечек ресурсов.

## Почему не GPL tun2socks

GPL-компоненты не включаются в закрытый проект без отдельного юридического решения. Для прототипа используются только MIT/Apache-2.0 компоненты.

## Этапы внедрения

1. Реализовать и протестировать локальный direct SOCKS5 TCP relay.
2. Добавить ограниченные очереди, статистику и корректное завершение соединений.
3. Собрать tun2socks из зафиксированных исходников для Android ABI.
4. Передать TUN fd в native/Go слой.
5. Оставить маршрут TEST-NET до прохождения интеграционных тестов.
6. Включить `0.0.0.0/0` только после успешного TCP passthrough на устройстве.
7. Добавить UDP relay и IPv6 отдельными проверяемыми шагами.

## Риски

- размер Go runtime и APK;
- совместимость gomobile/Android toolchain;
- задержка и расход батареи;
- корректность UDP association;
- DNS и IPv6 leaks;
- циклическая маршрутизация при незащищённом сокете;
- supply-chain риск большого дерева Go-зависимостей.

## Release gate

v0.2.0 нельзя считать готовой, пока не подтверждены:

- прямой TCP passthrough;
- прямой UDP passthrough;
- DNS;
- `VpnService.protect()` для каждого исходящего сокета;
- остановка без зависших потоков и file descriptors;
- не менее 30 минут стабильной работы на физическом Android-устройстве.
