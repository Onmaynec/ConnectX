# Архитектура ConnectX

## Назначение

ConnectX выполняет локальную обработку сетевого трафика Android-устройства, чтобы применять проверяемые методы противодействия DPI-разбору и принудительным разрывам соединений.

Это не удалённый VPN. Наличие системного значка VPN при использовании `VpnService` описывает Android API, а не маршрут трафика через сторонний сервер.

## Предварительная схема без root

```text
Приложения Android
        │
        ▼
локальный TUN (`VpnService`)
        │
        ▼
парсер IP/TCP/UDP и классификатор потока
        │
        ├── поток не требует обработки ───────────────┐
        │                                             │
        └── выбранная локальная стратегия обфускации  │
                                                      ▼
                                         защищённые исходящие сокеты
                                         (`VpnService.protect`)
                                                      │
                                                      ▼
                                       реальный сервер назначения
```

Собственные исходящие сокеты движка должны исключаться из TUN через `VpnService.protect()`, иначе возникнет цикл повторного перехвата.

## Что означает «скрывать трафик»

ConnectX не добавляет новое криптографическое шифрование поверх TLS и не способен сделать произвольный трафик невидимым провайдеру без второго удалённого узла.

Реалистичная цель локального режима — изменить наблюдаемое DPI представление отдельных соединений без изменения конечного назначения. Возможные классы методов требуют отдельной проверки:

- контролируемая фрагментация или сегментация данных рукопожатия;
- изменение порядка и размера локально отправляемых частей потока;
- работа с TCP-метаданными, доступными выбранному движку;
- выборочное управление QUIC/UDP;
- DNS-стратегии;
- root-режим с возможностями уровня пакетов, недоступными обычному приложению.

Ни одна стратегия не считается рабочей до реализации, сборки и проверки на реальной сети.

## Границы безопасности

- без удалённого сервера ConnectX;
- без MITM;
- без пользовательского центра сертификации;
- без расшифровки HTTPS;
- без чтения сообщений, паролей и содержимого страниц;
- без скрытых root-команд;
- без отключения SELinux.

## Архитектурные слои

1. **Android UI** — Compose, состояния подключения, настройки и диагностика.
2. **Service orchestration** — жизненный цикл foreground service и локального TUN.
3. **Tunnel engine** — чтение пакетов, управление потоками и прямые исходящие соединения.
4. **Strategy API** — подключаемые локальные стратегии обработки.
5. **Health checks** — проверка доступности и устойчивости без входа в аккаунты.
6. **Persistence** — настройки, результаты тестов и обезличенные технические журналы.

## Первый проверяемый прототип

Первый прототип не должен начинаться со сложной DPI-стратегии. Сначала требуется доказать, что приложение стабильно:

1. создаёт локальный TUN;
2. пропускает трафик напрямую без удалённого сервера;
3. не зацикливает собственные сокеты;
4. корректно обрабатывает остановку и смену сети;
5. измеряет TCP/UDP/IPv4/IPv6 поддержку;
6. предоставляет тестируемую точку включения стратегии.
