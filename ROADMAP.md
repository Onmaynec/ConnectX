# ConnectX Roadmap

> Статус: рабочий план разработки. Даты намеренно не фиксируются до появления стабильной скорости команды и матрицы реальных устройств.

## 1. Назначение продукта

ConnectX — Android-приложение для локальной обработки сетевого трафика и противодействия ограничениям DPI без обязательного удалённого сервера.

Приложение не является сервисом перенаправления трафика в другую страну. В обычном режиме Android `VpnService` используется только как системный API для создания локального TUN-интерфейса без root. Сетевой движок ConnectX должен открывать защищённые через `VpnService.protect()` прямые соединения к реальным серверам назначения.

ConnectX не выполняет MITM, не устанавливает пользовательский центр сертификации, не расшифровывает HTTPS и не читает содержимое сообщений.

## 2. Принципы выпуска

1. Нельзя называть стратегию рабочей до проверки на реальном устройстве и ограниченной сети.
2. Сначала создаётся стабильный passthrough, затем одна минимальная стратегия, и только потом автоматический подбор.
3. Каждый релиз должен собираться в GitHub Actions.
4. Каждый релиз получает тег, changelog, APK, SHA-256 и перечень известных ограничений.
5. Критические сетевые функции не заменяются незаметными заглушками.
6. Отсутствие удалённого сервера является архитектурой по умолчанию.
7. Функции root включаются только вручную и имеют механизм полного отката.
8. Логи не содержат содержимое пакетов, URL с параметрами, токены, cookies и сообщения.

## 3. Линии разработки

Работа разделена на шесть параллельных направлений:

- **Android shell:** приложение, Compose, жизненный цикл, разрешения и уведомления.
- **Tunnel:** локальный TUN, чтение и запись пакетов, маршрутизация и защита сокетов.
- **Network engine:** userspace TCP/UDP, DNS, IPv4/IPv6 и backpressure.
- **Strategies:** подключаемые методы DPI-обфускации и их capability model.
- **Quality:** unit/integration/device tests, fuzzing, профилирование и CI.
- **Product:** диагностика, исключения, настройки, приватность и выпуск.

## 4. Версии

### v0.1.0 — Foundation

**Цель:** создать собираемый и устанавливаемый каркас приложения, который корректно управляет системным разрешением локального VPN/TUN, но пока не заявляет рабочий обход.

#### Состав

- Android 10+ (`minSdk 29`).
- Kotlin, Gradle Kotlin DSL, Jetpack Compose и Material 3.
- Тёмная тема по умолчанию; поддержка системной и светлой темы.
- Главный экран ConnectX с реальными состояниями lifecycle.
- Экран с пояснением локальной обработки и отсутствия удалённого сервера.
- Запрос разрешения `VpnService.prepare()`.
- Foreground service с постоянным уведомлением.
- Создание и закрытие локального TUN-интерфейса.
- Безопасная остановка сервиса из UI и уведомления.
- Типизированная модель состояния соединения.
- Базовые unit-тесты модели состояний.
- GitHub Actions: compile, unit tests, debug APK artifact.
- README с инструкцией сборки.

#### Не входит

- Передача пользовательского трафика через TUN.
- TCP/UDP userspace stack.
- DPI-обфускация.
- DNS-over-HTTPS.
- Root-режим.
- Автоматический подбор стратегий.

#### Критерии готовности

- `assembleDebug` завершается успешно в чистом CI.
- Unit-тесты проходят.
- APK устанавливается на Android 10 и актуальный Android.
- Разрешение запрашивается только после действия пользователя.
- Сервис корректно создаёт и закрывает TUN.
- После остановки не остаётся активного foreground notification.
- Не заявляется, что обход блокировок реализован.

### v0.2.0 — Local Passthrough

**Цель:** получить локальный TUN-конвейер, который пропускает трафик напрямую к назначениям без DPI-модификации.

#### Состав

- Выбор userspace stack после licence review и прототипирования.
- IPv4 packet parsing.
- TCP passthrough.
- UDP passthrough.
- DNS passthrough.
- `VpnService.protect()` для всех исходящих сокетов движка.
- Ограниченные очереди и backpressure.
- Смена Wi-Fi/мобильной сети.
- Защита от циклического попадания соединений ConnectX обратно в TUN.
- Счётчики трафика и времени работы.
- Integration tests для start/stop/reconnect.

#### Критерии готовности

- Не менее 30 минут стабильного браузинга через локальный TUN.
- Отсутствие busy loop в простое.
- Корректное восстановление после потери сети.
- DNS, TCP и UDP работают на тестовой матрице.
- Нет утечек файловых дескрипторов по результатам длительного теста.

### v0.3.0 — First DPI Strategy

**Цель:** реализовать одну минимальную, измеримую и обратимую стратегию для TCP/TLS, не копируя Windows WinDivert-код.

#### Кандидаты исследования

- сегментация начальных TCP payload;
- управляемое разделение TLS ClientHello;
- изменение порядка отправки небольших фрагментов только при доказанной корректности;
- root-only TTL/desync как отдельный эксперимент, не часть обычного режима.

#### Состав

- `BypassStrategy` API и capability model.
- Одна стратегия без root.
- Ручное включение стратегии.
- Полное выключение без перезапуска устройства.
- Health check до/после применения.
- Измерение успешности соединений, задержки и ошибок.
- Набор тестовых доменов без входа в аккаунты.
- Feature flag для полного отключения стратегии.

#### Критерии готовности

- Стратегия улучшает доступ хотя бы в одной воспроизводимой тестовой сети.
- Не ухудшает обычные сайты за пределами согласованного порога.
- Не повреждает TLS и не требует MITM.
- Все ограничения отражены в UI и release notes.

### v0.4.0 — Diagnostics and Targets

**Цель:** дать пользователю понятную проверку доступности сервисов и технически полезный отчёт без сбора содержимого трафика.

#### Состав

- Диагностика DNS, TCP, TLS и HTTP safe endpoint.
- Карточки YouTube, Telegram, Discord и пользовательских доменов.
- Статусы: доступен, частично доступен, недоступен, тайм-аут, DNS error.
- Валидация доменов.
- Защита диагностических функций от локальных адресов и опасных URI.
- Экспорт обезличенного отчёта в файл.
- Автоматическая очистка старых журналов.

#### Критерии готовности

- Проверки не требуют авторизации пользователя.
- В отчёте отсутствуют токены, cookies, содержимое ответов и история страниц.
- Результат диагностики воспроизводим на тестовой сети.

### v0.5.0 — Strategy Selection

**Цель:** добавить несколько подтверждённых стратегий и безопасный автоматический выбор.

#### Состав

- Реестр стратегий.
- Экран ручного выбора.
- Автоматическое тестирование в безопасном порядке.
- Минимальное время жизни выбранной стратегии.
- Cooldown после ошибки.
- Защита от переключения туда-сюда.
- Сохранение последней рабочей стратегии для конкретного типа сети без постоянного идентификатора точки доступа.
- Отдельные capability-флаги TCP, UDP, IPv4, IPv6 и QUIC.

#### Критерии готовности

- Автоматический режим не переключает стратегию при единичной ошибке.
- Неработающая стратегия временно исключается.
- Пользователь всегда может перейти в ручной режим и выключить модификации.

## 5. Архитектурные этапы

### Этап A — Research gate

До включения внешнего движка требуется таблица:

- компонент;
- версия;
- upstream;
- лицензия;
- статическая или динамическая линковка;
- изменения ConnectX;
- обязательства распространения;
- совместимость с закрытым или открытым релизом ConnectX.

GPL-код нельзя копировать в проект без отдельного решения о лицензировании всего производного компонента.

### Этап B — Android shell

- `:app`
- `:core:model`
- `:core:designsystem`
- `:vpn:api`
- `:vpn:service`

На раннем этапе допускается ограниченное число модулей. Разделение расширяется после появления реальных границ, а не ради количества модулей.

### Этап C — Native engine decision

Сравниваются:

- Rust + JNI;
- C/C++ + JNI;
- существующий userspace stack с совместимой лицензией;
- минимальный собственный glue layer вместо самостоятельной реализации полного TCP stack.

Решение принимается после прототипа TCP/UDP passthrough и измерения APK size, CPU, latency и сложности отладки.

## 6. GitHub workflow

### Ветки

- `main` — только проверенные изменения.
- `research/*` — технические исследования.
- `feature/*` — продуктовые функции.
- `fix/*` — исправления.
- `release/*` — подготовка релиза.

### Pull requests

Каждый PR должен содержать:

- цель;
- ограничения;
- изменённые файлы;
- команды проверки;
- фактический результат;
- риски;
- связанные issues.

### Tags

- `v0.x.y` — экспериментальные и preview-релизы.
- `v1.x.y` — стабильная линия.
- Тег создаётся только после успешного CI на точном commit SHA.

## 7. Definition of Done для любой задачи

Задача считается выполненной, когда:

- код или документ находится в репозитории;
- нет скрытых критических заглушек;
- добавлены или обновлены тесты;
- выполнены доступные проверки;
- ошибки не замаскированы отключением тестов;
- UI-текст понятен на русском языке;
- приватность и rollback рассмотрены;
- issue содержит фактический результат.

## 8. Текущий приоритет

1. Завершить v0.1.0 Foundation.

4. После подтверждения выпустить `v0.1.0`.
5. Перейти к исследованию и прототипу v0.2.0 Local Passthrough.
